# 07 · Как писать скилл для агента

Скилл — половина продукта. Результаты pen.dev держатся на его скилле (правила вкуса, привычка проверять работу) не меньше, чем на API. Tusche поставляется со **своим** скиллом, написанным с нуля. Исходники: [`packages/skill/content/SKILL.md`](../../packages/skill/content/SKILL.md).

## Где живёт скилл

- Исходники: `packages/skill/content/`: `SKILL.md`, `pen-format.md`, `execute.md` и семь гайдов `guide/*.md` (версия 0.1.0, этап 1.6). Тесты проверяют ссылки, длину `SKILL.md` и то, что каждый `js`-блок гайда выполняется в `execute` без ошибок и предупреждений.
- Отдаётся MCP-инструментом `read_skill` (`SKILL.md` и файлы, на которые он ссылается). Поэтому скилл работает в любом MCP-клиенте без установки.
- Его можно поставить и как скилл Claude Code (`~/.claude/skills/tusche/`) для клиентов, которые поддерживают скиллы нативно.
- **Сам скилл пишется на английском:** английским инструкциям модели следуют надёжнее всего. Документация для разработки, включая этот документ, ведётся на русском; пользовательский гайд — на английском и русском (`docs/guide`).

## Структура

```
SKILL.md                 entry: what Tusche is, required reading, golden rules, workflow
pen-format.md            the schema in agent-oriented form (concise, examples, antipatterns)
execute.md               API reference + patterns (loops, components, verification visitors)
guide/
  web-app.md             dashboards, settings, tables, sidebars
  mobile-app.md          safe areas, tab bars, 390×844 screens, touch targets
  landing-page.md        sections, rhythm, hero patterns
  design-system.md       tokens, components first, variants, naming
  slides.md              16:9 frames, type scale for slides
  code.md                design → code and code → design workflows
  tailwind.md            mapping variables and layout to Tailwind v4
```

## Правила написания

1. **Инструкции, а не эссе.** Короткие пункты в повелительном наклонении. Каждое правило должно окупать свои токены.
2. **Рядом с паттерном показывай антипаттерн.** Ограничения модели усваивают быстрее всего из пар «НЕПРАВИЛЬНО / ПРАВИЛЬНО».
3. **Закладывай проверку как привычку:** собрал секцию → проверил visitor'ом (`ctx.problems`) → снял скриншот этой секции → исправил на месте. Никогда не удалять и не пересобирать.
4. **Описывай вкус явно.** Назови типичные признаки «сгенерированного ИИ» дизайна и запрети их: карточки вокруг всего, градиентная каша, три одинаковых блока с фичами, всё по центру, огромные тени, эмодзи вместо иконок.
5. **Держись формата.** Никакого мышления в терминах CSS: ни margin, ни процентов, ни переноса. Скилл должен совпадать с проверками `pen-format` один в один: если валидатор что-то отвергает, скилл обязан об этом сказать.
6. **Раскрывай постепенно.** `SKILL.md` не длиннее ~250 строк; подробности — в файлах, на которые он ссылается, и агент читает их только по необходимости.
7. **Версионируй.** У скилла есть версия, и каждое изменение проверяется агентными эвалами (см. ниже).

## Как оценивать скилл

Бенчмарк лежит в [`evals/`](../../evals/README.md), решения — в [ADR-010](adr/010-skill-evals.md).

| Набор | Что меряем |
|---|---|
| 10 экранов: веб, мобильный, лендинг, дашборд, слайды, дизайн-система; две задачи на русском | новые замечания `lint` (из них layout и шрифты), оставшиеся `placeholder`, вызовы `execute` и неудачные, исправления через `editId`, `undo`, токены, ходы |
| 5 правок реального `fixtures/pen/eval/design.pen` | то же плюс размер диффа и верхние ноды, изменённые вне `scope` (правки инстансов, токенов, компонентов) |
| Оценка людьми | вслепую по контакт-листу (`evals/src/sheet.ts`): вкус от 1 до 5, два ревьюера |

Каждая задача — отдельная сессия `claude -p` с одним MCP-сервером `tusche`, без встроенных инструментов и пользовательских настроек. Изменение скилла принимается, только если `evals/src/compare.ts` не нашёл ухудшений относительно `evals/baseline/`.

## Стилевые архетипы

`get_style` дополняет скилл: если пользователь не задал направление, агент выбирает архетип, а не изобретает очередную синюю SaaS-страницу. Каждый архетип **оригинальный** (название, палитра, пара шрифтов, правила) и идёт с готовым набором для `SetVariables`. В фазе 1 их 8: `quiet-editorial` (editorial), `blueprint` (технический), `soft-play` (игривый), `night-shift` (тёмный продуктовый), `bento-grid` (bento), `raw-concrete` (бруталистский), `mono-minimal` (минималистичный монохром) и `warm-market` (тёплый потребительский). Тест проверяет контраст текста и акцента при всех значениях параметров.

Шрифты архетипов обязаны покрывать латиницу и кириллицу: многие акцидентные шрифты Google Fonts только латинские, и русский текст молча уходит в запасной шрифт. Так было с Fraunces в первом прогоне сценария 1 (2026-10-20): теперь это ловит предупреждение `missing-glyphs`, а в `quiet-editorial` заголовочный шрифт заменён на Lora. Покрытие всех архетипов проверяет `bun packages/styles/scripts/check-fonts.ts`: латиница и кириллица во всех ролях шрифтов, без `missing-glyphs` и `unknown-font`. Кириллицу кандидата сначала смотрим в метаданных Google Fonts (subset `cyrillic`): латинские Space Grotesk, Archivo, DM Sans, Bricolage Grotesque, Instrument Serif и Fraunces не подходят.
