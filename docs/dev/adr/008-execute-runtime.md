# ADR-008 · Модель выполнения `execute`: asyncify-сборка QuickJS, транзакции на хосте

- **Статус:** Принято
- **Дата:** 2026-10-20
- **Уточняет:** [ADR-003](003-quickjs-execute-sandbox.md), [ADR-007](007-pen-scene-projection.md), [06-agent-api](../06-agent-api.md)

## Контекст

ADR-003 выбрал QuickJS в WebAssembly и оставил бенчмарк сборок на этап 1.4. Когда начали писать `@tusche/exec`, выяснилось ещё три вещи.

1. **Раскладка асинхронная.** `scene.layout` подгружает шрифты (Google Fonts, кэш на диске). `Get` и `FindEmptySpace` обязаны видеть несохранённые правки того же вызова, значит, посреди сниппета хост иногда должен ждать. Сниппет агента при этом пишется синхронно: `const b = Get(id, visit)`.
2. **Сцена привязана к одному документу.** Правки иммутабельны, каждая даёт новый объект `PenDocument`, а `PenProjection` строила индекс, резолвер переменных и набор символов шрифтов один раз в конструкторе.
3. **Ноды внутри инстанса правятся не там, где лежат.** У `inst/child` нет своей ноды в файле: правка — это запись в `descendants` инстанса.

Бенчмарк `bun packages/exec/scripts/bench-quickjs.ts` (quickjs-emscripten 0.32.0, Bun 1.3.14, Windows 11; медиана 5 прогонов, два запуска):

| Сборка | Загрузка модуля | Рантайм + контекст | 10⁴ хост-вызовов с JSON | Visitor по 1000 нод с хоста |
|---|---|---|---|---|
| QuickJS sync | 15–18 мс | 0,6–0,9 мс | 54–75 мс | 9–10 мс |
| QuickJS-ng sync | 7 мс | 0,6–0,7 мс | 51–76 мс | 9–14 мс |
| QuickJS asyncify, хост отвечает сразу | 10–12 мс | 0,7–0,8 мс | 103–146 мс | 16–21 мс |
| QuickJS-ng asyncify, хост отвечает сразу | 10–11 мс | 0,9–1,1 мс | 114–158 мс | 19–26 мс |
| QuickJS asyncify, каждый вызов ждёт | 10–19 мс | 1,0–1,1 мс | 262–282 мс | 36–39 мс |
| QuickJS-ng asyncify, каждый вызов ждёт | 14–15 мс | 1,4–1,5 мс | 282–333 мс | 42–49 мс |

Asyncify медленнее синхронной сборки в 1,5–2 раза, но visitor по 1000 нод всё равно укладывается в 16–21 мс. Это в 15 раз меньше бюджета N1 (300 мс), а основное время `Get` уходит на раскладку, а не на VM. QuickJS-ng заметно не выигрывает.

Альтернатива asyncify — синхронная сборка с предзагрузкой шрифтов до запуска сниппета. Но шрифты нужны тем текстам, которые сниппет только что вставил. Пришлось бы перезапускать сниппет после дозагрузки, а это сложнее и хрупче.

## Решение

1. **Сборка:** `quickjs-emscripten-core` + `@jitl/quickjs-wasmfile-release-asyncify` (QuickJS Беллара). Модуль WASM — один на процесс, вызовы `execute` идут через очередь (asyncify допускает одну приостановку на модуль).
2. **Хост отвечает синхронно, когда может.** Асинхронно (с приостановкой VM) работают только операции, которым нужна раскладка или рендер, если сцена ещё не готова. Всё остальное — обычный возврат значения.
3. **Контекст на вызов.** `module.newContext()`: контекст владеет своим рантаймом. Отдельный рантайм с живыми хост-функциями в 0.32.0 падает при освобождении. Лимиты: память 256 МБ (`setMemoryLimit`), стек, дедлайн 10 с — обработчик прерываний в VM и проверка дедлайна в хост-функциях: время раскладки тоже считается.
4. **Граница VM — JSON-строки.** Внутри VM работает наш пролог на JS: обёртки API, ленивое дерево для visitor'ов (дети, `ctx.bounds`, `ctx.problems` — геттеры, которые идут на хост по требованию) и разбор ошибок. Хост-объекты в VM не попадают.
5. **Транзакция — ссылка на корень `PenDocument`.** Правка копирует путь от корня до ноды (`withChanges`, `createNode`), откат — возврат старой ссылки. Запись файла, `Export`, скриншоты и сохранение глобальных переменных выполняются только после коммита.
6. **Сцена следует за документом.** `scene.update(doc, roots)` меняет документ проекции и пересобирает затронутые корни. Затронуты корень каждого изменённого пути и корни, которые (транзитивно) ссылаются на изменённые компоненты. После `SetVariables` затронуты все корни. Перед чтением в середине вызова сцена получает документ транзакции, при откате — закоммиченный.
7. **Правки внутри инстанса** превращаются в `descendants` ближайшего инстанса из документа: `Update` — переопределение (`children` в нём задаёт детей целиком), `Replace` — замена с `type` и новым id, адрес `inst/<новый id>`. `Insert`, `Delete` и `Move` для нод компонента внутри инстанса — ошибка с подсказкой (`Update(path, {children})`, `Update(path, {enabled: false})`). Ноду, которая физически лежит в документе (внутри `children` переопределения или замены), правят на месте. Поведение сверено с pen.dev (см. §2 [06](../06-agent-api.md)).

## Последствия

- ➕ Сниппеты остаются синхронными и короткими; `Get` видит правки вызова и шрифты новых текстов.
- ➕ Откат бесплатный, частично применённых правок не бывает: побочные эффекты идут после коммита.
- ➕ Пути из ошибок, `bounds` и предупреждений — те же, что принимает API (ADR-007).
- ➖ Asyncify-сборка в 1,5–2 раза медленнее синхронной на хост-вызовах. На сниппетах дизайна это миллисекунды.
- ➖ Одна приостановка на модуль: параллельные `execute` по разным документам идут по очереди. Для фазы 1 (один агент) этого достаточно. Если понадобится параллельность — по модулю на сессию.
- ➖ Лимит памяти срабатывает не всегда быстро. Одна большая аллокация или рост массива упираются в него за миллисекунды. Но когда сниппет копит крупные строки, у самого лимита QuickJS запускает сборку мусора на каждой аллокации, и такой вызов заканчивается по лимиту времени, иногда с опозданием на 1–2 с: нативный `repeat` и сборщик мусора не прерываются. После нехватки памяти модуль WASM пересоздаётся (~10 мс): в одном из замеров следующий `newContext` упал с `call_indirect to a signature that does not match`.
- ➖ Переполнение стека asyncify-сборка бросает на стороне хоста, а не возвращает как ошибку сниппета, поэтому у такой ошибки нет номера строки.
- ➖ Пересборка идёт по корню целиком: правка большой доски стоит её полной раскладки (2–3 с на `app.pen` и `main.pen`). Инкрементальная проекция — отдельная задача.
