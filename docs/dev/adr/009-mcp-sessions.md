# ADR-009 · Сессии MCP: активный документ, undo, отложенная запись, слежение за файлом

- **Статус:** Принято
- **Дата:** 2026-10-20
- **Уточняет:** [04-architecture](../04-architecture.md) §«Сессии, файлы и конкурентный доступ», [06-agent-api](../06-agent-api.md) §1, [ADR-008](008-execute-runtime.md)

## Контекст

На этапе 1.4 `DocumentSession` пишет файл сразу после каждого успешного коммита. Undo и слежения за файлом нет. Для MCP-сервера (этап 1.5) этого мало:

1. Каждый инструмент принимает необязательный `filePath`, но в 06 не сказано, какой документ считать активным.
2. В 04 есть стек undo, но в 06 нет ни одного инструмента для него.
3. В 04 упомянут дебаунс записи. С ним появляется состояние «несохранённые изменения», а без него `save_document` не нужен.
4. Правило про конфликт в 04 противоречит само себе: «изменился на диске → перезагрузить», но «коммит агента новее изменения на диске → конфликт». Не сказано, как отличить свою запись от чужой.

## Решение

1. **Активный документ** — последний документ, который открыли или передали в инструмент через `filePath`. Относительные пути считаются от рабочего каталога процесса MCP. Если документ не указан и активного нет, инструмент возвращает ошибку с подсказкой вызвать `open_document`.
2. **Undo и redo** — отдельные MCP-инструменты `undo` и `redo` с необязательным `steps`.
   - Один шаг — одна закоммиченная транзакция `execute`, в которой изменился документ.
   - Глубина стека — 50 шагов.
   - Шаг возвращает документ и глобальные переменные к состоянию до транзакции. Упавшие сниппеты (`editId`) остаются.
   - Новый коммит очищает стек redo.
   - Снимок стоит дёшево: документ иммутабелен, нетронутые поддеревья общие (ADR-008).
3. **Отложенная запись.**
   - `Executor` принимает режим сохранения: сразу (по умолчанию; так работает CLI) или с задержкой `delayMs`. MCP-сервер использует задержку 300 мс.
   - До записи сессия «грязная», `get_app_state` это показывает.
   - Запись немедленно выполняют `save_document`, `render`, `lint`, закрытие сессии, закрытие stdin и выход процесса.
   - Ошибка записи даёт предупреждение `save-failed` в ответе ближайшего инструмента. Сессия остаётся грязной, следующий коммит или `save_document` пробует записать снова.
4. **Слежение за файлом** работает по запросу, без фоновых watcher'ов.
   - Сессия хранит хэш содержимого, которое она последней прочитала или записала.
   - Перед каждым инструментом MCP сравнивает этот хэш с хэшем файла на диске.
   - Файл изменился, а несохранённых правок нет: документ перечитывается. Глобальные переменные сохраняются, стеки undo и redo очищаются, в ответ добавляется предупреждение `reloaded`.
   - Файл изменился, а несохранённые правки есть: это **конфликт**. Сессия ничего не трогает, `get_app_state` и `execute` сообщают о конфликте, `execute` отказывается работать.
   - Конфликт разрешают два пути: `open_document` с `reload: true` принимает версию с диска, `save_document` перезаписывает файл версией сессии.
   - Файл удалён: в первом случае сессия закрывается, во втором это тоже конфликт.
5. **События изменений.** `DocumentSession.onChange` сообщает о коммите, undo, redo и перезагрузке. Это задел для preview (этап 1.7).

## Последствия

- ➕ Чужая правка (pen.dev, git checkout, редактор) подхватывается на следующем вызове агента без фонового процесса и без гонок с собственной записью.
- ➕ Серия быстрых `execute` пишет файл один раз. Undo агент делает одним вызовом, а не встречным сниппетом.
- ➕ CLI и тесты этапа 1.4 не меняются: по умолчанию запись немедленная.
- ➖ Конфликт обнаруживается только на следующем вызове. Окно между коммитом и записью (300 мс) остаётся; при аварийном завершении процесса последняя правка может потеряться.
- ➖ Хэш считается по всему файлу перед каждым инструментом. Для файлов в единицы мегабайт это миллисекунды; если станет заметно — сначала сравнивать `mtime` и размер.
- ➖ После перезагрузки undo пуст: отменить правку, сделанную до чужого изменения, нельзя.
