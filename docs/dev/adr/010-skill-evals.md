# ADR-010 · Эвалы скилла: `claude -p` с изолированным MCP, журнал вызовов, правило приёмки

- **Статус:** Принято
- **Дата:** 2026-10-20
- **Уточняет:** [07-skill-authoring](../07-skill-authoring.md) §«Как оценивать скилл», [ADR-004](004-agent-connection.md), [ADR-009](009-mcp-sessions.md)

## Контекст

В 07 сказано, что изменение скилла принимается, только если автоматические метрики эвалов не ухудшились. К этапу 1.6 нет ни задач, ни раннера, ни метрик. MCP-сервер не считает вызовы, структурного диффа `.pen` нет.

Агента для эвала можно запускать двумя способами:

1. **Субагентами в живой сессии** через подключённый у разработчика MCP `tusche`. Это дёшево в настройке, но окружение у каждого своё: пользовательский CLAUDE.md, другие MCP-серверы (в том числе pen.dev), скиллы. Токены точно не посчитать.
2. **`claude -p` в headless-режиме** со своим MCP-конфигом. Окружение повторяемо, stream-json даёт токены, ходы, стоимость и модель. Тратится квота Claude разработчика.

## Решение

1. **Основной раннер — `claude -p`** (`evals/src/run.ts`). Каждая задача идёт отдельной сессией во временной папке вне репозитория, чтобы не подхватился CLAUDE.md. Флаги: `--strict-mcp-config --mcp-config` (только `tusche` из этого репозитория), `--tools ""` (без встроенных инструментов), `--setting-sources local`, `--allowedTools mcp__tusche`, `--no-session-persistence`, `--max-turns 80`, `--output-format stream-json --verbose`. Промпт — текст задачи как есть, без подсказок.
2. **Ручной режим.** `evals/src/score.ts --task <id> --pen <file>` оценивает файл, собранный субагентом или руками. Метрики сессии и вызовов в этом режиме — `null`.
3. **Журнал вызовов.** Если задан `TUSCHE_CALL_LOG=<файл>`, `tusche mcp` дописывает JSON-строку на каждый вызов инструмента: инструмент, успех, время. Для `execute` в записи ещё `editId`, `retryOf`, счётчики изменений, коды предупреждений и число изображений. Для `read_skill` — файл, для `get_style` — стиль, для `undo` / `redo` — шаги. В `createServer` это опция `onCall`. Без переменной поведение не меняется.
4. **Метрики** (`score.json` на задачу, `metrics.json` + `summary.md` на прогон):
   - замечания `lint`, появившиеся по сравнению с исходным файлом, и отдельно layout и шрифты;
   - оставшиеся `placeholder`;
   - вызовы `execute`, неудачные, исправления через `editId`, `undo`;
   - токены, ходы, стоимость;
   - для правок — изменённые строки относительно исходника и верхние ноды вне `scope`.

   Исходник для диффа — фикстура после миграции и записи writer'ом. Writer сохраняет стиль (ADR-006), поэтому построчный дифф честный.
5. **Правило приёмки** (`evals/src/compare.ts`) считается по суммам набора. Строго не должны расти: несозданные файлы, ошибки сессий, замечания lint, layout, шрифты, `placeholder`, неудачные `execute`, правки вне `scope`. Строки диффа и токены могут вырасти не больше чем на 15 %. Наборы задач у сравниваемых прогонов должны совпадать.
6. **Оценка людьми** — вслепую по контакт-листу (`evals/src/sheet.ts`): случайные коды, `ratings.csv` и отдельный `key.json`. В правило приёмки не входит.
7. **Baseline** — `evals/baseline/metrics.json` и `summary.md`. Это закоммиченный прогон текущей версии скилла. Рендеры и транскрипты не коммитятся (`evals/runs/` в `.gitignore`).

## Последствия

- Прогон baseline — 15 сессий `claude -p`. Это ощутимая часть квоты, поэтому эвалы не входят в `bun run check` и CI. Запускаются вручную при изменении скилла.
- У агентов большой разброс. Один прогон — шумная точка, поэтому сравниваются суммы набора, а у токенов есть допуск. Если разброс мешает решать, следующий шаг — несколько прогонов на задачу и медианы.
- Модель по умолчанию — та, что настроена в CLI. Она записывается в `metrics.json`. Сравнивать можно только прогоны с одной моделью.
- `--tools ""` отключает и поиск отложенных инструментов. Если CLI начнёт откладывать MCP-инструменты, раннер нужно поправить: агент останется без `execute`, и это сразу видно по `execute = 0`.
