# ADR-002 · `.pen` — родной формат, его дерево — источник истины

- **Статус:** Принято
- **Дата:** 2026-10-20

## Контекст

У пользователей уже много `.pen`-файлов. Формат опубликован; это JSON, удобный и для git, и для агентов (`fit_content`, `ref` + `descendants`, переменные с темами). Реальные файлы на диске — **обычный JSON, без шифрования**, вопреки старым утверждениям. OpenPencil умеет читать `.pen`, но не умеет его записывать, а его импортёр теряет несколько типов нод и заливок.

Варианты:

1. Сделать документом `.fig` / scene graph OpenPencil, а `.pen` импортировать и экспортировать. Потери в обе стороны, файлы пользователя меняют форму.
2. Свой новый формат. Ломает совместимость, а ещё один формат никому не нужен.
3. **`.pen` — модель документа, scene graph OpenPencil — производная проекция.**

## Решение

Вариант 3.

- `@tusche/pen-format` владеет `PenDocument`: схема, валидация, миграции, каноническая сериализация.
- Все правки — и от агента, и ручные из фазы 2 через обратный маппер — это операции над `PenDocument`.
- `@tusche/pen-bridge` инкрементально проецирует `PenDocument` в `SceneGraph` для layout, рендера и экспорта. Проекцию можно выбросить и построить заново.
- Неизвестные и неподдерживаемые свойства сохраняются в `PenDocument` байт в байт.
- Tusche пишет канонический JSON (стабильный порядок ключей, без значений по умолчанию), чтобы диффы оставались маленькими.

## Последствия

- ➕ Файлы остаются совместимыми с pen.dev; круговая конвертация точная; git-диффы чистые.
- ➕ API для агента работает в терминах `.pen` — в тех же, которым учит скилл.
- ➖ Придётся поддерживать свой мост, а не полагаться на `@open-pencil/pen`. При этом внутри можно переиспользовать его конвертеры и отправлять улучшения в upstream.
- ➖ В фазе 2 руками можно будет менять только те свойства, у которых есть аналог в `.pen`.
- ➖ Мы следуем формату, который контролирует другая компания. Как снижаем риск: миграции по версиям, политика «неизвестное сохраняем», ориентир — публичная схема.
